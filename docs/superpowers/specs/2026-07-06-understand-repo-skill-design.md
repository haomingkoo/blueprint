# Design: `/understand-repo` skill

Date: 2026-07-06
Status: approved (pending implementation plan)

## Summary

A new Claude Code skill, shipped inside this repo, that takes a local repo
path and produces a verified, logically-grouped explanation of the whole
codebase — not just the structural graph Blueprint already builds, but a
semantic layer on top of it: what each module does, and how modules cluster
into subsystems. Every semantic claim is generated by one agent, then
independently checked by a second before it's kept, and every claim carries
its supporting evidence — same discipline as Blueprint's existing
`"structural"`/`"heuristic"` confidence tiers, extended with a new
`"semantic"` tier.

Output is written to a SQLite DB (queryable) and a small multi-page HTML
site (readable), one snapshot per run, kept as history rather than
overwritten.

## Problem

Blueprint's existing analyzer (Slices 1-8) is 100% structural: it observes
files, manifests, and regex-detected imports, and never claims to know what
code *means*. That's honest, but it caps how well a large, unfamiliar
codebase can be explained — a big repo's module list doesn't add up to a
narrative a new joiner can hold in their head. This skill adds that
narrative layer, without weakening the accuracy guarantee that makes
Blueprint's existing output trustworthy: nothing here reports a claim it
hasn't verified against real code.

## Relationship to existing work

- Reuses `analyzer.analyze_local_repo` (the same function `server/main.py`
  already imports) for the structural pass — no re-implementation, no new
  file-content scanning at that layer.
- Reuses the existing `Node`/`Edge` import graph (`build_graph`) as the
  objective backbone for subsystem clustering.
- Distinct from `docs/issues.md`'s Slice 9 ("Analysis History", which caches
  *structural* JSON to skip re-cloning). This skill's versioned "sweeps" are
  a separate history of the *semantic* layer and don't replace Slice 9 —
  worth reconciling later if both end up wanting a shared history UI, but
  out of scope here.
- Not part of the Slice 1-9 numbering — this is a new, additive tool, not a
  continuation of the existing web app.

## Goals

- Given a local repo path, produce a verified semantic summary per module
  and a logical grouping of modules into subsystems.
- Every semantic claim is independently adversarially verified before being
  kept; unverified claims are dropped, never silently invented.
- Output is both machine-queryable (SQLite) and human-readable (multi-page
  HTML site + Markdown report).
- Zero new runtime dependencies (stdlib `sqlite3`, existing Workflow tool
  for the agent fan-out).
- Repeat runs keep history rather than clobbering prior sweeps.

## Non-goals

- Not a replacement for Blueprint's existing structural graph/report/export
  (Slices 1-8) — this sits alongside it, reusing it as ground truth.
- Not a general-purpose doc generator for arbitrary non-code content.
- No cross-repo comparison, no incremental/partial re-sweep (a re-run is
  always a full sweep) — YAGNI until proven needed.
- No new node/edge types beyond what `analyze.py` already detects (module,
  dependency) — clustering works with what exists today.

## Architecture

Five stages, each consuming only real output from the stage before it:

1. **Structural pass (no LLM).** Calls `analyzer.analyze_local_repo(path)`
   directly, producing the existing `RepoIndex` (files, manifests, modules,
   nodes, edges). Unchanged from today's Blueprint.

2. **Clustering pass (no LLM, plain Python).** Groups module-type nodes into
   subsystems via connected components over the existing `"imports"`
   module→module edges. Deterministic and reproducible: the same repo
   always clusters the same way, fully explainable by real edges already on
   disk. A module with no import edges to/from any other module becomes a
   singleton subsystem — clustering never fails or requires a fallback path.

3. **Semantic fan-out (ultracode, pipelined one stage per module).** For
   each module:
   - Agent A reads the module's `key_files` and writes a summary that must
     cite specific files/functions as evidence.
   - Agent B, independently, re-reads the same files and attempts to
     refute Agent A's summary against the actual code.
   - Only claims Agent B can't refute are kept, tagged
     `confidence="semantic"`. Anything refuted is dropped, not edited —
     a dropped claim is safer than a patched-up guess.

4. **Synthesis pass (one agent, given only verified output).** Reads the
   verified per-module summaries, the cluster assignments, and the real
   inter-cluster edges; writes a name + one-paragraph narrative per
   subsystem and a top-level "how this repo fits together" summary. This
   agent narrates stage 1-3's output — it does not introduce new structural
   claims of its own.

5. **Populate outputs.** Writes everything to SQLite and renders the
   Markdown report + multi-page HTML site (below).

## Data model

SQLite (stdlib `sqlite3`), one connection per sweep, everything keyed by
`sweep_id` so history is queryable (e.g. diff a subsystem's narrative
across two sweeps):

- `sweeps`: id, repo_path, repo_name, commit_sha, branch, started_at,
  finished_at.
- `modules`, `nodes`, `edges`: mirror the existing `Module`/`Node`/`Edge`
  dataclasses (plus `sweep_id`); confidence stays `"structural"`/
  `"heuristic"` as today — this table is a straight dump of `RepoIndex`,
  nothing new claimed here.
- `subsystems`: sweep_id, name, narrative.
- `module_subsystem`: sweep_id, module_name, subsystem_id (join table from
  clustering).
- `semantic_summaries`: sweep_id, module_name, summary_text,
  evidence_files (json), verified (bool), confidence="semantic". Only rows
  that survived Agent B's adversarial pass exist here.

## Output layout

```
blueprint/.understanding/<repo-name>/
  <timestamp>-<short-sha>/
    understanding.db
    report.md                    # structural + verified semantic + synthesis narrative
    site/index.html              # overview + subsystem list, links out
    site/subsystem-<name>.html   # one page per subsystem
  latest -> <timestamp>-<short-sha>/   # convenience pointer, updated each run
```

Gitignored, lives entirely inside this repo's own workspace — never writes
into the repo being swept, since that repo may not be owned/controlled by
the user running the sweep. Each run adds a new `<timestamp>-<short-sha>/`
directory rather than overwriting the previous one; `latest` always points
at the most recent.

All HTML pages are self-contained (inline CSS reusing `html_export.py`'s
existing dark-theme styles, no external requests), linked to each other
with relative paths only.

## Confidence tiers (updated)

| Tier | Meaning | Existing/new |
|---|---|---|
| `structural` | Directly observed (a file/dir/manifest exists) | existing |
| `heuristic` | Regex-inferred (import scanning) | existing |
| `semantic` | LLM-derived, independently adversarially verified against real code | **new, this skill** |

A `semantic` claim is never presented without having survived Agent B's
refutation attempt. This is the load-bearing accuracy guarantee for the
whole skill — every downstream output (DB rows, HTML, Markdown) only ever
shows verified claims.

## Error handling

- Bad path or a failed structural analyze → clean error, no `sweeps` row
  created, no agents spent.
- A module where Agent B refutes everything → the module still appears
  (structural facts + cluster assignment), with an explicit "no verified
  semantic summary this sweep" note — never silently dropped from output.
- An agent call failing outright (Workflow's `agent()` resolves to `null`
  on a dead subagent) → treated the same as a fully-refuted module: falls
  back to structural-only, logged, sweep continues for other modules.
- Clustering itself has no failure mode (worst case: N singleton
  subsystems for a repo with no inter-module edges).

## Testing

- Clustering algorithm, DB writer/schema, HTML/Markdown renderers: real
  pytest unit tests against a fixture `RepoIndex`, same convention as the
  existing `analyzer/test_slice*.py` files (deterministic, no network, no
  LLM calls).
- The three LLM stages (summarize / verify / synthesize) aren't unit
  testable in the traditional sense. Verified by one real manual sweep
  against an actual repo (e.g. this blueprint repo itself, or a small
  public repo already used in prior slices' verification), with the
  resulting summaries hand-reviewed for hallucination as the "done" check
  — same spirit as the Playwright screenshot QA gate used in Slices 6/7,
  adapted to reviewing text accuracy instead of visual layout.

## Open questions / deferred

- Whether `module_subsystem` should ever allow a module in more than one
  subsystem (currently: no, connected components gives a strict partition).
  Revisit only if a real repo's clustering looks wrong in practice.
- No UI/command for browsing sweep history yet beyond the `latest` symlink
  and querying the DB directly — deferred until there's a concrete need to
  compare sweeps.
